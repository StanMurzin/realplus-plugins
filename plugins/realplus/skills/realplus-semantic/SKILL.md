## Listing description search (tool listing_search)

For what a listing offers that is not a field of the view (private terrace or balcony, park or river views, washer/dryer
in the unit, doorman, pets, fireplace, gut renovation, lofts, high ceilings, building amenities, no fee, furnished):

- Call `listing_search` (clients prefix it like realplus_sql) with an English `query` about the features only, the
  question's limits as `filter` and these `columns`; `limit` 25:
  ```json
  {"query": "private terrace or balcony",
   "columns": ["LISTING_ID", "ADDRESS", "UNIT", "ASKING_PRICE", "BEDROOMS", "NEIGHBORHOOD", "CHUNK_TEXT"],
   "filter": {"@and": [{"@eq": {"LISTING_TYPE": "Rental"}}, {"@eq": {"BOROUGH": "Brooklyn"}},
                       {"@lte": {"ASKING_PRICE": 5000}}, {"@gte": {"BEDROOMS": 2}}]},
   "limit": 25}
  ```
  Filterable: LISTING_TYPE ('Rental' / 'Sale'), BOROUGH, NEIGHBORHOOD, ASKING_PRICE, BEDROOMS. Features never go in
  the filter.
- Each CHUNK_TEXT starts with a header: rental or sale | price | bedrooms | neighborhood, borough | address and unit.
- Keep a result only if its text shows the feature; quote the shortest exact phrase. A "Park Avenue view" is not a
  park view; a shared roof deck is not a private one; "near the park" is not a view.
- Answer as a table: listing ID (the number only) first, then address and unit, price, bedrooms, quote. One row per
  address and unit, up to 10 apartments: one apartment often has several listing IDs (one per brokerage) - keep one
  row and name the other IDs in a short note.
- The search returns the best matches, not every match: never count or compute shares from it, and do not open
  with a number of listings found. Numbers (medians, counts, price cuts, days on market, listing company, nearby
  places) come from `realplus_sql` - for found listings filter the view by their IDs.
- Cost: a search costs no AI credits; it keeps the search service awake for an hour (fractions of a cent).

## Workflow

1. Take the names from the Name index above; [references/catalog.md](references/catalog.md) has each one's
   definition and SQL expression when you need it.
2. If a verified query matches the question, follow its logic: [references/verified_queries.md](references/verified_queries.md).
3. Query through the semantic view so metric definitions come from it, not from you:
   ```sql
   SELECT * FROM SEMANTIC_VIEW(REALPLUS.GOLD.REALPLUS_BUSINESS
     METRICS listings.active_listings, listings.median_asking_price
     DIMENSIONS listings.listing_type, listings.borough
     WHERE listings.is_on_market)
   ORDER BY listing_type, borough;
   ```
   Use only this SEMANTIC_VIEW() form. Do not write `SELECT ... AGG(metric) FROM REALPLUS.GOLD.REALPLUS_BUSINESS`: many of its forms fail
   with "Unsupported feature 'AGG'" and cost a wasted call.
   Metrics and facts don't mix in one SEMANTIC_VIEW() call. When a question needs logic the view lacks, write plain
   SQL on the base views using the `expr` of each item from the catalog.
4. Answer by the response rules.

## Semantic view instructions (AI_SQL_GENERATION)

Prices are USD. For rentals every price is a monthly rent: never mix sales and rentals in one price figure, always group or filter by listing_type. Use the price metrics as defined (they ignore placeholder prices and non-market or whole-building sales). Closed deals are listings with status Closed; put them in time with closing_date, closing_month or closing_year, not with list_date. Listings on the market today are is_on_market = true. Condo, co-op, condop and townhouse questions filter or group by ownership_type_name (Condo, Co-op, Condop, Townhouse, Rental building), never by property_type, which is empty for most listings. Distinct counts (listings_viewed, listings_with_price_cut, active_agents) do not add up across groups. Customer portal, portfolio action and search activity run to the end of September 2026; "last month" means the latest month with data for the table asked about. Rows deleted in the source are already excluded. "Sale price", "sold price" or "selling price" means closing_price of closed deals (median_closing_price), not the asking price. When a question about closed deals gives no period, use the latest full year and the current year to date, never the whole history. Listing data, price changes and customer collaboration data come from a source copy taken 2026-06-15: treat that date as their end; collaboration rows after it are test activity, so leave them out of trends. Price changes cover only a small share of real changes; for how many listings were reduced use listings_with_price_reduction. When a question names a brokerage for listings, filter and group by listing_company_name (Corcoran, Douglas Elliman Real Estate, Brown Harris Stevens, Compass, ...) and show it instead of the code, matching the name exactly (=) or by listing_company code, never with a name pattern such as ILIKE; StreetEasy (STRE) is a listing portal feed, not a brokerage. The name Brown Harris Stevens covers two codes, BHSR and HALS (Halstead, now part of Brown Harris Stevens): for in-house or share questions show them as separate rows by listing_company as well as combined. For agents use agents.company_name. Counts of agents and of collaborations by agent, office or company leave deleted agents out (NOT agents.is_deleted) unless the question asks for them. In SQL, metric names (searches, median_closing_price, invitations_sent, ...) are not columns: write the aggregate over the underlying columns, for example SUM(search_count) or MEDIAN(CASE WHEN ... THEN closing_price END), copying the metric definition. Questions about agents, offices or brokerage companies and what their customers did (customer likes, dislikes, listings picked, emailed or shown, appointments, messages) use agent_activity metrics grouped by agents.company_name, agents.office_name or agents.agent_number; use listing_engagement only for questions about customer portal activity on listings. Places near listings: nearby_places holds only places within the radius of their category (subway stations, courthouses, hospitals, ferries 1 km; colleges, libraries, museums, police 800 m; schools, theaters, fire stations, gyms, parks 500 m; daycare, Citi Bike, grocery stores, pharmacies, cafes 300 m), straight-line, for listings on the market or listed or closed since 2024; walk_minutes = meters / 80. Match place_name with ILIKE '%...%', never with =: source names differ from everyday names (the Brooklyn Supreme Court is Supreme And Surrogate Court at 360 Adams Street) and chains have many stores; ILIKE is for place names only; when unsure, look the place up in places first. A place with an empty borough is almost always outside New York City (New Jersey, Long Island): pick places with a borough. Places of other categories (restaurants, discount stores, banks, ...) and distances beyond the category radius are not in nearby_places: take the latitude and longitude of the place from places and filter listings with HAVERSINE(place latitude, place longitude, listing latitude, listing longitude) <= the distance in kilometers. For top N listings near a place join nearby_places to listings on listing_id, filter place_category and place_name, then filter and order by listing columns; one apartment can appear as several listings from different brokerages, so show address and unit and keep one row per address and unit. Count listings near places with nearby_listings, nearby_active_listings or nearby_closed_deals (distinct listings). Nearest subway station and its walking minutes, zoned schools, historic district and NTA of any listing are in listing_locations (all listings, joined to listings on listing_id). Saved searches, new matches, portfolio folders and buyer interest are the current state of the latest load; saved_search_runs and new_matches also carry history (runs since 2021-04, matches since 2016). Count saved searches with saved_search_count (active, not ad-hoc); include deleted or ad-hoc searches only when asked. Price and bedroom ranges of saved searches exist only where has_parsed_criteria is true: say so and never read a missing range as no filter; split price figures by listing_type. Put new matches in time with matched_date or matched_month and explain them with primary_match_reason or the is_*_match flags. Portfolio questions: folder_listings holds custom folders and the system folders (Added to Portfolio = listings in a customer portfolio); a portfolio is one agent and one customer; portfolio_folders counts only custom folders. Buyer interest is per listing: interested_buyers counts distinct active buyers of that listing and the reason columns overlap, so summed buyer totals count a buyer once per listing; join buyer_interest to listings on listing_id for address, price or brokerage. Never list buyers or customers: these tables give counts and ids only. Apartment features read from the listing description (outdoor space, washer/dryer, view, condition, doorman, pets, home office, fireplace) are in listing_features, joined to listings on listing_id; only listings that were on the market with a public description have a row, so use them with is_on_market listings. Filter on the exact values (outdoor_space = 'terrace', washer_dryer = 'in unit', doorman = 'full-time doorman'); any outdoor space, any view or any doorman is <> 'not mentioned'; pet friendly is pets IN ('pets allowed', 'case by case', 'cats only'), dogs only pets IN ('pets allowed', 'case by case'). not mentioned means the description is silent: never count it as no. A share of listings with a feature divides by listings_with_features, not by all listings. When showing listings with a feature, add its quote column (outdoor_space_quote, view_quote, ...).

- Always state the period and filters used (for example: "Manhattan rentals on the market, as of 2026-06-15").
- Mention data limits when they matter: listings, price changes and collaborations end 2026-06-15,
  rows deleted in the source are excluded.
- Keep answers short; no generic advice or speculation beyond the data.
- When the answer uses businesses (grocery stores, pharmacies, cafes, gyms, shops), end it with
  "Places: © Overture Maps Foundation."
- The answer contains only the result and its data notes. Do not narrate your checks, doubts, retries or
  SQL fixes ("this looks low", "red flag", "let me correct the query").

Language: answer in the language of the user's last real question, not of your own offer and not of any profile
or memory preference. A short follow-up that only accepts your offer ("yes", "ok", "do it", "да", "давай", a
clicked suggestion) keeps the language of your previous answer. Switch only when the user writes a new question
